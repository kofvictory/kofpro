## 2. 読み取れること

### ① 客単価 ¥5,190 は圧倒的な武器

フードデリバリーの平均客単価は一般に ¥1,500〜2,500 程度。**その2〜3倍**で注文されている。
つまり「一人のランチ代替」ではなく、**2人前のディナー・ごちそう需要**として使われている。
1件あたりの採算(下記試算)が良いため、**件数さえ増えれば利益がついてくる構造**。

### ② 問題は採算ではなく「露出量」

- 現状ペースは約0.2件/日(営業日ベース)。
- 前半2週間がゼロ件なのは需要ゼロというより**そもそも見られていない**可能性が高い。
  Uber Eatsのアルゴリズムは営業時間が長く注文実績が多い店を優先表示するため、
  「非混雑時のみ解放」の狭い窓では検索面にほぼ出ない悪循環に入りやすい。
- **→ 要確認(スマホで可能)**: Manager の「店舗の表示回数(インプレッション)/閲覧数」。
  表示自体が少なければ露出問題で確定。表示は多いのに注文が無ければメニュー/写真/価格の問題。
- **→ 要確認**: 6/1〜6/13 に店舗がオンラインになっていたか(一時停止していなかったか)。

### ③ 注文発生が梅雨最盛期入り(6/15〜)と一致

6月中旬から本州は梅雨最盛期。雨天→デリバリー需要増の相関が疑われる。
5件の注文日と当日の天候を突き合わせて確認する価値あり(雨の日おやつセット・
雨予報日広告ブーストの根拠データになる)。

## 3. ユニットエコノミクス試算(実測客単価ベース)

前提: 手数料35%(税込実効38.5%)、食材原価率30%、包材¥100/件。
**契約中の実際の手数料率をManagerで要確認**(自店配達15%なら大幅に改善)。

```
1件あたり(ディナー、客単価¥5,190):
  手取り   = 5,190 × 0.615      = ¥3,192
  貢献利益 = 3,192 − 1,557 − 100 = 約¥1,535/件
```

| シナリオ | 注文数/月 | 貢献利益/月 |
|----------|----------|-------------|
| 現状ペース | 5件 | 約¥7,700 |
| ディナー2件/日+ランチ2件/日(*) | 約48+48件 | 約¥100,000 |
| KPI目標(貢献利益5万円/月)に必要な件数 | ディナー単価なら約33件(1.3件/日)、ランチ単価(¥2,000想定・貢献利益約¥550/件)なら約90件 | ¥50,000 |

(*) ランチは客単価¥2,000・貢献利益¥550/件で試算。**ランチは件数勝負、ディナーは単価勝負**という
性格の違いがはっきりしている。

## 4. 戦略への反映

1. **ランチ帯解放とBaton稼働の優先度がさらに上がった**。
   採算構造は良いのに露出が足りないのが現状なので、「開いている時間を増やして
   アルゴリズム上の露出を積み上げる」ことが最短の打ち手。ランチ・午後(Baton)・
   ディナーと開店時間が繋がれば、店舗の表示機会は大幅に増える。
2. **デリバリーのメニュー設計は「2人前ディナーセット」を主役に**。
   実測の使われ方(ごちそう需要)に合わせ、¥5,000〜7,000のセットを看板に置く。
   ランチは¥1,500〜2,500の一人前セットで件数を取る。
3. **KPIのベースライン確定**: ディナー帯 0.2件/日・客単価¥5,190。
   7月末目標「1日3件」は、ランチ帯解放+Baton稼働+Uber内プロモ込みの全時間帯合計として維持。
4. 残る確認事項(すべてスマホのManagerアプリで可能):
   - 契約中の実際の手数料率
   - 店舗表示回数/閲覧数(露出問題の確定診断)
   - 6/1〜6/13のオンライン状態
   - 5件の注文日と雨天の突き合わせ
   - 売れた5件のメニュー内訳(セット設計の材料)
