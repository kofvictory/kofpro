# 05. ロードマップ構築フレームワーク — 12週サイクルと AI への任せ方

## 設計原則(ロードマップを AI に作らせる前に押さえること)

1. **遅行指標は目標に、先行指標は計画に**
   登録者数・収益・入選は遅行指標(直接コントロールできない)。計画に載せるのは先行指標=自分の行動(公開本数・撮影行回数・応募数・商品公開数)だけ。遅行指標は月次レビューで観測するのみ。
2. **12週=1クール**
   1年の計画は必ず狂う。見通せる最長が12週。1年は「4クール+各クール間の見直し」として扱う。
3. **時間予算が先、タスクが後**
   店の営業が主変数。先に「使える時間」を確定し(定休日×何時間+営業日朝×何時間)、その**8割**までしか計画に入れない。2割は必ず余白(繁忙・トラブル・気力の変動)。
4. **縮退運転(minimum viable week)を最初に決める**
   繁忙週でも落とさない最低ライン(例: Shorts 1本 or 撮影行1回のどちらか)を決めておく。ゼロの週を作らないことが継続の技術。
5. **4領域ポートフォリオ**
   Quotidiano の4領域(店舗売上 / YouTube / 写真・コンペ / 語学・開発)のうち、この文書群が扱うのは YouTube・写真・マネタイズ。店舗は trattoria ブランチ側の計画が正。クールごとに「今クールの主役領域」を1つ決め、他は維持モードにする。
6. **ロードマップはマスターデータ、日々のタスクは派生物**
   ロードマップ(このフレームで作る文書)が単一の真実源。KofPro LifeLog の entries はそこから派生する実行単位。逆流(思いつきタスクの積み上げ)で計画を上書きしない — 思いつきは Inbox に入れ、週次レビューでロードマップと突き合わせてから採用する。

## 構造(上から下へ導出する)

```
ビジョン(1〜3年)         例: 伊語圏に届くチャンネルが育ち、写真がコンペで評価され、創作が月N万円を生む
  └ クールゴール(12週・最大3つ)   測定可能な状態で
      └ 月マイルストーン(3段階)     クール内の中間チェックポイント
          └ 週次スプリント            今週やる3つ(完了条件つき)
              └ 日次アクション          LifeLog の「今日」ビューに出るもの
```

## KofPro LifeLog との接続

| ロードマップ側 | LifeLog 側 |
|---|---|
| 週次スプリントの3タスク | QuickCapture で登録 → トリアージで「着手」 |
| 思いつき・新アイデア | まず Inbox へ。週次レビューまで採用しない |
| 週次レビュー | 「今日」「着手中」ビューの消化実績を材料に実施 |
| 見送り判断 | トリアージの「見送り/保留」に理由を残す(次クール設計の材料になる) |

## ひな型2: 週次レビュー(毎週・15分)

```
週次レビューです。15分で終わる密度で頼みます。

## 実績(LifeLog より)
- 計画していた3タスク: {{各、完了/未完と一言}}
- 実際に使えた時間: {{N}}時間(計画比 {{+/-}})
- Inbox に溜まった思いつき: {{列挙}}
- 数字の動き(あれば): {{再生・登録・売上など}}

## 依頼
1. 未完タスクの原因を「時間 / スキル / 気力 / 段取り」のどれかに分類(複数可)
2. Inbox の思いつきを「今クールに採用 / 次クール候補 / 見送り」に振り分け(ロードマップとの整合を根拠に)
3. 続けること / やめること / 変えること を各1つ
4. 来週の3タスク(各: 完了条件 / 想定時間 / どの時間帯に置くか)
5. 縮退運転が必要な週か判定(店の繁閑: {{来週の見込み}})

## 条件
- 励ましは不要。事実と次の一手だけ
- 3週連続で同じ原因が出ていたら、計画側の構造問題として指摘すること
```

## ひな型3: 月次レビュー(月1・60分 / スナップショット更新とセット)

```
月次レビューです。[スナップショット] の更新も兼ねます。

## 実績
- 今月の先行指標: 公開{{N}}本 / 撮影行{{N}}回 / 応募{{N}}件 / 商品進捗{{...}}
- 遅行指標の観測: {{登録者・再生・収益・コンペ結果}}
- アナリティクス診断(02のひな型7)の結果: {{要点を貼る}}

## 依頼
1. 月マイルストーンに対する進捗判定(順調 / 遅れ / 前提が変わった)
2. 遅れている場合: 「頑張って取り返す」以外の選択肢を3つ(削る・ずらす・やり方を変える)
3. 先行指標と遅行指標の関係に見えてきた兆候(例: ○○系の動画だけCTRが高い)
4. [スナップショット] の改訂版全文(そのまま保存できる完成形で)
```

## ひな型4: クール末レビュー(12週ごと・90分 / 次クール設計へ)

```
クール末レビューです。今クールの総括と、次クールの設計方針を出してください。

## 材料
- クールゴール3つの達成状況: {{...}}
- 月次レビュー3回分の要点: {{貼る}}
- 今クールのロードマップ: {{貼る}}
- 主観の総括: {{楽しかったこと / 消耗したこと / 発見}}

## 依頼
1. 達成・未達の要因分析(未達の何割が「計画の過積載」由来かを必ず評価)
2. 4領域(店舗 / YouTube / 写真 / 語学・開発)のバランス診断と、次クールの主役領域の提案
3. 次クールのクールゴール候補を5つ → 私が3つ選ぶための判断材料(効果 / 工数 / 飽きのリスク)
4. 時間予算の見直し提案(実績データに基づく現実的な週{{N}}時間)
5. この総括を、次クールのロードマップ生成(ひな型1)にそのまま貼れる500字要約に圧縮
```

## ひな型5: ロードマップの中途改訂(前提が崩れたとき)

クール途中の大きな変化(繁忙期の延長・機材トラブル・バズによる方針転換)に使う。全部を作り直さない。

```
ロードマップの前提が変わったので、部分改訂してください。

- 現行ロードマップ: {{貼る}}
- 変わった前提: {{例: 7〜8月の繁忙で時間が週N→N/2時間に / EP01が想定の3倍再生されている}}
- 動かせないもの: {{コンペ締切など}}

## 依頼
1. 影響範囲の特定(どのゴール・週が影響を受けるか)
2. 改訂案を2つ: A案=ゴールを守りタスクを削る / B案=ゴール自体を縮小する。それぞれの代償を明記
3. 推奨案と、改訂後の週次プラン表(残り週ぶんの完成形)
4. 「変えなくてよいもの」の明示(過剰反応の防止)
```

## 年間の流れ(まとめ)

| タイミング | やること | 使うひな型 |
|---|---|---|
| クール頭 | ロードマップ生成 → LifeLog に第1週ぶん登録 | 05-1(必要に応じ 02-1, 03-1, 04-3 を先に) |

| クール末 | 総括90分 → 次クール設計 | 05-4 → 05-1 |
| 随時 | 前提が崩れたら部分改訂 | 05-5 |
