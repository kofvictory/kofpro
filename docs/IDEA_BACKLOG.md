## 1. スタイルチェンジ型のモード拡張(エグゼのスタイルチェンジ発想)

**着想**: ロックマンエグゼの「スタイルチェンジ」= 使い方に応じてナビの姿・特性が変化する。
これを「賢いモード」の延長として、**用途特化のモードチェンジ**に発展させる。
既存の「賢いモード(Claude)」は“頭脳の格を上げる”軸。ここに“**役割を切り替える**”軸を足すイメージ。

### 方向性
- **特化モード(ペルソナ＋ツールセットの切替)**: モードごとに systemPrompt とツール構成を差し替える。
  頭脳(モデル)は据え置きでも、役割特化で“別スタイル”に見せられる(③テーゼ「人格は外側」の応用)。
- 候補モード例(いずれも仮):
  - **集中/実行モード**: 今日のタスクだけに絞り、雑談を抑え、着手を促す。
  - **発想/ブレストモード**: 造語や飛躍を許容、アイデアを広げる(温度高め)。
  - **記録/ログモード**: 受け取った情報を淡々と分類・保存に徹する(能動提案を抑制)。
  - **調査/リサーチモード**: 外部情報や手順の深掘りに寄せる(将来的にweb等)。
- **見た目の変化**: モードごとにコフの配色・エフェクト・アイコンを変える(スタイルチェンジの視覚的快感)。
  ※アバターの見た目確定はEP06(キャラ確立編)以降。ここと連動させると強い。
- **切替UI**: 「賢い」トグルの隣に、モード選択(タブ/リング/ショートカット)。

### 動画的な旨み
- 「1体のコフが、用途で姿と性格を変える」= スタイルチェンジ回として単独で映える。
- ③テーゼ(人格は外側＝systemPrompt＋ツール)を、モードの数だけ実証する構図になる。

### 論点/未決
- モードの粒度(増やしすぎると迷う)。既定モードと、切替コストのバランス。
- 頭脳(ローカル/Claude)軸 × 役割(モード)軸 の2次元をUIでどう見せるか。

## 2. KofPro を“PET(パーソナルターミナル)”へ強化

**着想**: エグゼの PET = 生活に常時帯同する個人端末＋相棒の container。
KofPro を単なるライフログ＋チャットから、**生活全体の個人ターミナル**へ寄せる。

### 方向性
- **常駐と帯同の強化**: フローティング常駐(EP01で最小実装)の発展。デスクトップの“常に居る窓口”化。
  将来的にモバイル/別デバイスとの連携で「どこでもコフが帯同する」PET感。
- **入出力の多様化(DEVLOGフェーズ4と接続)**: 音声入力、画像添付、通知/能動リマインド。
  “話しかける・見せる・呼びかけられる”で、端末というより相棒の窓口に。
- **生活の一元ハブ化**: 現状の entries(task/idea/log/note/decision/event)を軸に、
  1日の入口(朝のブリーフィング)と出口(夜の振り返り)をコフが担う“定点”に。
- **状況認識(コンテキスト)**: 時間帯・作業状況・場所などに応じてコフの振る舞いが変わる。
  (1のモードチェンジと連動:文脈で自動的にスタイルが変わる、等)
- **パーソナル化**: 使うほどコフが持ち主の傾向を掴む(triage_decisions等の蓄積を活用)。
  “自分だけのナビ”という企画の芯を、機能面から裏打ちする。

### 動画的な旨み
- 「タスク管理アプリ」から「自分のPET」への進化そのものがシリーズの縦の成長物語になる。
- PET化は企画の原点(ネットナビへの憧れ)への回帰。回を重ねるほどテーマが強化される。

### 論点/未決
- スコープ肥大の危険(何でも屋にしない)。“定点/窓口”という軸を外さない。
- プライバシー/ローカル完結の担保(常時帯同・状況認識と表裏)。ローカル優先の設計思想と整合させる。
- どこまでをアプリ機能、どこからを演出(動画上の見せ方)にするかの線引き。

## 3. ナビの切り替え選択機能 ＋ 専用ナビ「調査ナビ」

**着想**: スタイルチェンジ(§1)とは**明確に別物**。§1は「コフ1体の役割・振る舞いを切り替える」のに対し、
こちらは**性能・特性が根本から異なる複数のナビを持ち、切り替えて選択する**機能。
エグゼで言えば、スタイルチェンジではなく「ナビそのものを乗り換える」に近い。KofProが“ナビたちのPET”になる方向。

### 方向性
- **ナビ切替の基盤**: ナビ=「人格(systemPrompt)＋ツールセット＋頭脳(モデル)＋UI(アバター/カラー)」の1セット。
  コフはその第1号。ナビごとに**大幅な性能変更**(使うモデル・持つ道具・振る舞い)を許容する。
  ③テーゼの発展形:「人格は外側」だからこそ、セットごと差し替えれば“別のナビ”が成立する。
- **切替UI**: ナビ選択画面(PETのナビ切替イメージ)。フローティングアバターもナビごとに交代。
- **第1号の専用ナビ「調査ナビ」(仮)**:
  - 役割: 持ち主の**好みに合わせたニュース・情報収集係**。
  - 動き: 関心領域(例: NPU/ローカルLLM/個人開発)を学習・設定し、定期巡回→要約→ブリーフィング。
  - コフとの分担: コフ=生活とタスクの相棒(定点) / 調査ナビ=外の世界を見てくる斥候。
  - 技術要素: Web検索/フィード取得、要約パイプライン、関心プロファイル(entriesやタグから抽出も検討)。

### 動画的な旨み
- 「2体目のナビが生まれる」= シリーズの世界が広がる大きな節目回になる。
- コフと調査ナビの掛け合い(調査ナビが集めた情報をコフがタスク化する等)は、エグゼ的な“ナビのいる生活”の画をさらに強くする。
- キャラ確立編(EP06)の後に置くと、確立した手法で2体目を作る、という積み上げが見せられる。

### 実装メモ:調査ナビの「NPU自律収集」
**着想**: 調査ナビ選択中は、NPUが自律的に情報収集・選別を回し、定期的に新着をブリーフィングする挙動。
→ 現実的、かつ **NPUの本来の得意分野と噛み合う**。宙に浮いていたNPUに最初の実用的な居場所を与える案。

- **なぜNPU向きか**: 走らせたいのはLLMの巨大生成ではなく、**軽量・高頻度・常時稼働**のタスク(記事の分類/スコアリング、埋め込みベクトル化、重複・類似判定)。これはNPUが省電力で担う想定の仕事。CPU/GPUを食わず裏で回せる=「邪魔せず勝手に働く相棒」の体験と一致。
- **処理の3段分解**: ①定期巡回(スケジューラでフィード/検索取得) → ②選別(関心プロファイルと照合して要否・順位付け) → ③要約＆通知(ブリーフィング)。
- **役割分担(重要)**: **選別=NPU**(件数多・高頻度・軽量でNPUが最も効く) / **要約=既存ハイブリッド**(重い生成は 普段ローカルLLM／賢いモードでClaude)。①デモの“必要なときだけ賢く”の思想をそのまま適用。
- **NPU化の現実性**: 埋め込み・分類の小型モデルを ONNX Runtime + QNN で動かすのは、7B級LLMを丸ごとNPUに載せるより現実的。**LLM本丸より先に「NPUクエストの最初の勝利」を拾える**可能性がある(⑧で保留した宿題の“部分回収”)。
- **段階設計(安全策)**: まず **NPU無し(CPUで選別)でも成立する形**で作り、NPU化は後から差し込む。選別処理のバックエンドを差し替え可能にしておく(OLLAMA_HOST 環境変数化と同じ発想)。
- **⑥の伏線回収**: 「NPUで動いてるつもり=実はCPU」の教訓どおり、**タスクマネージャーのNPU使用率で“実際に動いている証拠”を撮る**のは必須。これは EP01⑥で植えた伏線が、この回でようやく回収される構図になる(シリーズをまたぐ設計上の旨み)。
- **地道な難所**: 情報源の安定性、ノイズ/重複/誤情報の扱い、通知頻度がうるさくなりすぎない設計。AI以前の作り込みだが体験を左右する。

### 論点/未決
- §1(スタイルチェンジ)との棲み分けをUI上どう見せるか(モード切替とナビ切替が混ざると迷う)。
- 調査ナビの情報源と品質管理(誤情報・ノイズ)。ローカル/クラウドどちらの頭脳を既定にするか。
- ナビ間のデータ共有範囲(調査ナビはentriesをどこまで読み書きするか)。
- 増やしすぎ注意: ナビは「役割が明確に立つ」単位でのみ追加する。

## 5. ローカルコフ候補モデル ＋ NPU対応モデルの現状（2026-07 調査）

> Web調査で裏取りした候補整理。KofProの条件(Snapdragon X / Ollama / 日本語 / Function Calling)前提。
> ローカルLLMは動きが速いので、実装前に最新版・対応状況を再確認すること。現行既定は qwen2.5。

### ローカルコフの“頭脳”候補（Ollama = CPU推論）
- **Qwen3 系（本命）**: 日本語トップクラス＋native tool callingがchat templateに内蔵、OllamaのtoolsAPIでそのまま動く。Apache 2.0。現行 qwen2.5 からの自然な進化。単発ツール利用は小型(〜9B)、多段エージェントは27〜35B級。
- **Llama-3-ELYZA-JP-8B / Swallow（日本語特化）**: Llama系の日本語追加学習版。Ollama利用可。日本語の自然さが売り。ツール呼び出しの安定性はQwen系が上。
- **Llama-3-Groq-Tool-Use（ツール特化）**: BFCLトップ級。ツール呼び出しに全振りしたい場合。
- **Granite 4 / Gemma 3**: function calling対応。Gemma3は4Bなど軽量枠にも。
- **軽量枠**: Gemma 3 4B / Qwen3 1.7B・4B / Phi-4-mini。
- 実務注意: ツール定義10個で1,000トークン超を消費。小型モデルはツール数を5〜10に抑える（KofProは現状ツール約10個 → 小型化時は要削減）。
- 接続: OllamaはOpenAI形式でtool定義を受け取る → KofProの翻訳レイヤー(EP01④)とそのまま噛み合う。

### ⚠ NPUの現状（EP01⑥の裏取り・EP02の直接素材）
- **Ollama / LM Studio は Windows ARM では CPU専用。NPUは使われない**（＝⑥の壁の実証）。
- **NPUを解放する道 = ONNX Runtime + QNN 系スタック**:
  - **AnythingLLM**: QNN SDK経由で Hexagon NPU上でLLM＋埋め込みを実行。ONNXバックエンド対応。
  - **Foundry Local**: CPU/GPU/NPU でローカル実行＋API提供。Phi Silica等のNPU最適化モデル。
  - **Nexa SDK**: Llama-3B / Phi4-mini / Qwen3-4B 等がNPUで動作。クエリ時にNPU使用率がスパイク（＝“実際に動いてる証拠”が撮れる）。
  - **ONNX Runtime GenAI（QNN）**: Phi-3.5-mini 等を Snapdragon NPU で。Qualcomm最適化済みアセット配布あり。
- **NPU化の現実的な入口**: Phi-3.5-mini / Llama-3.2-3B の既製NPUアセット、または Qwen3-4B（NPU対応版）。7B級LLM丸ごとより、まず小型＋埋め込み/分類から。
- **§3(調査ナビ)との接続**: 選別=埋め込み/分類 は NPU が最も効く領域。NPU化の最初の実用はここで拾える可能性。

## 6. 【定期レビュー】賢いモード用オンラインLLM(API)のコスパ比較

> **一度きりでなく定期的に見直す項目。** モデルとAPI価格は数ヶ月単位で更新されるため、都度「最良コスパ」を再評価する。
> 現行の賢いモードは Anthropic API(claude-haiku-4-5)。これを基準に、他候補と定期的に比べる。

### 見直しの観点
- **コスパ**: 入力/出力トークン単価 × KofProの実利用パターン(短い対話中心＋ときどき長い提案)での実効コスト。
- **品質**: 日本語の自然さ、能動提案の質、Function Calling(tool use)の正確さ・安定性。
- **統合コスト**: 既存の翻訳レイヤー(EP01④)で吸収できるAPI形式か。移行の手間。
- **レイテンシ / レート制限 / 可用性**: 常駐エージェントとして実用的か。
- **プライバシー / データ利用ポリシー**: ローカル優先の思想と矛盾しないか。

### 比較候補(都度、最新の価格・モデルで更新)
- Anthropic Claude(現行 Haiku 系 / 上位 Sonnet 系) ← 現行基準
- OpenAI GPT 系(mini/nano 級のコスパ枠)
- Google Gemini 系(Flash 級)
- DeepSeek / GLM / Qwen 等のクラウドAPI(コスパ重視枠)
- その他、賢いモードのフォールバック先として妥当な新規モデル

### 運用ルール
- **レビュー頻度**: 四半期ごと、または新モデル/大幅値下げの報せがあった時。
- **記録**: 見直すたびに「日付 / 候補 / 実効コスト試算 / 品質所感 / 採否」をこの項に追記(履歴を残す)。
- **判断の非対称性**: 乗り換えは統合・検証コストを伴うため、明確なコスパ/品質差がある時のみ。小差なら現行維持。
- **動画ネタ化**: 「賢いモードのAPIを比較して選び直す」回はコスパ実測ネタとして単独で成立しうる(SERIES_ROADMAP候補にも)。
- ※価格・モデルは変動が速い。検討時は必ず各社の最新の公式価格を確認してから試算する。
